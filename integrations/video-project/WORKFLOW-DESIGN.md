# 三阶段制作规程

口播正文是内容依据；RunDesk/Codex 负责判断与执行，Video App 提供服务、版本和产物记录。用户一键制作初稿已经授权日常制作，不在三个阶段之间重复设置确认门槛。终稿仍要求对具体完整输出的人审。

| 阶段 | 主要决策 | 可检查产物 |
| --- | --- | --- |
| 素材准备和对齐 | 阅读全文；取得真实配音时序；查看已有图片/多帧视频；按表达需要生成素材；保存具体文字引用和素材的关系 | plan/media 记录、配音、素材、持久化关联表及未覆盖范围 |
| 剪辑 | 依据关联和配音安排画面、字幕、声音；采用一个剪辑后端 | 原生 DSL 或 video-use EDL、真实完整初稿 |
| 精修 | 查看实际成片，按问题和人的文字意见局部修改，保留其他满意部分 | 新输出、检查记录、仍未验证的事项 |

内容可自由组织，不强制段落镜头、一句一图或合成块切点。关联表只定位引用和决策；DSL/EDL 只表达剪辑。一个画面可覆盖多个文字片段，一个意思也可使用多个画面。

## 持久化的文字与素材关系

`video_media_alignment_get/update` 保存针对精确 `narrationText` 哈希的引用、视觉意图、真实素材 ID、可选视频源时间、证据/示意/背景/文字卡角色、理由和选择状态。引用必须能在原文中定位，重复引用需指定出现次序。关联单元无须预先完整切分全文；服务返回未覆盖范围，Agent 据此补足表达。

实际图片通过 MCP 图像结果送给视觉模型，视频多帧检查只提供采样证据。已有 `video_media_align` 是描述词项检索，不等于完成视觉语义判断。生成的图片或视频先作为实际素材导入，再检查和关联，不能把任务成功当作内容合格。

TTS 使用实际合成块时序，可能带静音补齐，不冒充逐字对齐、ASR 核验或人工听审。board 的 `sourceHash` 是保存正文精确 UTF-8 SHA256，与 TTS 内部 `scriptHash` 不可互换。

## 一个剪辑后端、一份权威工程

`workflow.editingBackend` 默认为 `native`，旧项目无需迁移。原生后端继续使用已有 DSL、App 渲染和局部补丁。显式选择 `video_use` 才使用共享工作目录、生产快照和脚本素材适配器，不同步写一份原生 DSL。

`video_production_run_prepare` 冻结并导出当前第一阶段输入；Agent 按返回路径写 EDL 并调用适配器；`video_production_run_ingest` 验证、归档真实成片。适配器第一版提供连续外部配音、图片/视频单视觉轨道和字幕，不声称具有原生叠层/音乐的全部能力。精修新建生产快照，沿用剪辑决策并刷新导出路径，不修改已归档工程和输出。

## 参考与验证边界

借鉴 [browser-use/video-use](https://github.com/browser-use/video-use) 的文本驱动编辑、项目记录和输出检查。输入以用户撰写的主播稿为主，因此没有照搬从原始视频转写开始的流程，也没有在每次视觉切点对连续配音做淡化。

工具检查通过不等于所选 RunDesk 模型确实收到了图像；这需要真实模型联调。渲染帧采样不等于观看全片或听过声音。Agent 检查完成不等于人审。第三阶段应记录采样时间、实际检查和未完成事项。

`bridge.go` 基础 Skill 与随包 `SKILL.md` 保持完全相同；`workflow.go` 的三个逻辑 Skill 保持旧 ID 兼容，但分别聚焦准备和对齐、剪辑、精修。安装名称跟随 App 版本，旧自定义 Skill 不被覆盖。
